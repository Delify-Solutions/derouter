## 3. Daily refund sweep

- [x] 3.1 Create `src/lib/billing/cacheMissRefund.js`, same shape as `src/lib/billing/expiry.js` (unref'd daily interval, re-entry guard, fail-open, `globalThis` singleton); register it from `src/shared/services/initializeApp.js`'s `runHeavyStartup()`, matching `expiry.js`'s own registration comment.
- [x] 3.2 Implement the sweep per design.md decision #4: group `pending` detections by `userId`, refund in detection order up to `cacheMissRefundDailyCapNanoUsd` for that user that day, insert one `creditLedger` row per refunded detection (`kind: "refund"`, `requestKey` derived from the detection id for idempotency, `usageId` = the detection's `usageHistoryId`), set `status: 'auto_refunded'`, `ledgerId`, `resolvedAt`. Detections beyond the cap stay `pending`.
- [x] 3.3 Before writing the credit step, read `insertLedgerSync` and the plan-queue-billing window-recompute path (`userPlanWindows`'s "counters recomputed from the ledger" convention) to confirm whether inserting the ledger row alone restores available credit, or whether a window counter also needs a direct nudge — do not assume; verify in code. **Finding: the ledger row alone is NOT sufficient.** `userPlans.creditRemainingNanoUsd` (the actual spendable balance `chargeSync`/`bookBalanceNanoSync` read) is mutated DIRECTLY by `chargeSync`/`adjustCreditSync`; it is never derived by summing the ledger, so a bare `refund` ledger row would record the event while leaving the customer unable to spend the money back. `refundIntoPlanSync` therefore does the same direct `UPDATE userPlans SET creditRemainingNanoUsd = ...` `adjustCreditSync` uses, alongside the ledger row. `userPlanWindows` (the rate-limit counters) deliberately are NOT nudged: `rebuildWindowsSync` only ever replays `kind = 'charge'` rows by design, and `adjust`/`expire` rows already don't touch windows either — a window counts that a request happened and spent quota at the time, which stays true after a later refund of its price; nudging it down would let refund-then-respend exceed the window's limit. See the long comment at the top of `cacheMissRefund.js`.
- [x] 3.4 Implement the fallback from design.md's first Risk: if the original charge's `userPlanId` (found via `creditLedger.usageId = usageHistoryId`) no longer resolves to an open plan, credit into the user's current active paying plan instead (same resolution a new request's charge would use), and record the fallback in the ledger row's `meta`. Never fail the whole sweep for one user's unusual case — skip that detection (leave it `pending`) and continue with the rest.
- [x] 3.5 Tests (`test/cache-miss-refund-sweep.test.js`): under the cap (all refunded); over the cap (partial refunded, rest stay pending); re-running the sweep twice never double-refunds; the original plan missing falls back correctly; one user's failure does not block another user's refunds in the same sweep run.
